# Step 128.27.22 — G-SUB Comprehensive Remaining Work Audit

## 1. Executive summary

G-SUB has substantial implemented stage-specific workflows, dashboards and role checks. The largest course-demo risks are **unverified integration across the whole current workflow**, lack of reviewer-friendly selection and configured anonymity, incomplete professor-requested navigation/progress design, and an unverified explanation for apparently missing Demo records. Formatting and publication are implemented as a **local prototype**; real DOI registration and public publication are not implemented. Current source and historical stage tests are evidence of functionality, not proof that a complete present-day demonstration succeeds.

The owner now prioritizes a complete, stable classroom demonstration. This audit therefore recommends a short synthetic full-workflow and persistence baseline first, followed by focused demo improvements. It does **not** recommend resuming enterprise lifecycle/authentication or email-worker expansion unless a demonstrated blocker requires it. A finite A/B/C implementation sequence is in [the companion roadmap](step_128_27_22_demo_roadmap.md).

Evidence legend: **Completed** means the specifically scoped implementation is present, not a current end-to-end certification. **Partially Implemented** means code exists but requested coverage, integration or policy is incomplete. **Not Started** means no implementation was found in inspected active source. **Needs Product Decision** and **Requires External Integration** identify dependencies; an existing related prototype is still described. Demo readiness below means **code present / unverified now**, unless explicitly described otherwise. Complexity S/M/L is relative effort, not a schedule.

## Addendum — mandatory readability, fifth role and multi-format uploads

The owner explicitly added all three requirements as **Priority A**. The existing four-card screenshot is historical visual guidance; it no longer overrides the required fifth Formatter card. ### Global readability audit and acceptance

Inspect computed foreground/background pairs, not merely the palette, across login/role selection; Author, Editor, EIC, Reviewer and Formatter dashboards; navigation/sidebar; buttons, forms, inputs and placeholders; tables, cards, dialogs and badges; notification panels, progress and errors; and normal, selected, disabled, hover and focus states on light and dark surfaces. `frontend/src/index.css` supplies a font but no global foreground/background; `App.css` has a global `h1` color, `.footer-text` uses `#94a3b8` on a white card and disabled controls use opacity. `RoleSelection.css` supplies dark surfaces, accent text and explicit focus outlines. `AuthorDashboard.css`, `EditorDashboard.css`, `ReviewerDashboard.css`, `EICDashboard.css`, `InitialEditingPanel.css`, `ManuscriptProgress.css` and `NotificationBell.css` mix explicit and inherited colors; `FormattingPanel.jsx` and the Formatter dashboard also reuse shared styles. Native inputs/buttons and nested components without explicit colors can inherit or render differently under browser/OS themes. These are **inspection targets**, not a claim that every combination fails contrast; no visual or contrast measurement was run here.

Acceptance: measure rendered combinations and correct all identified unreadable text, including placeholder and state variants; target WCAG AA 4.5:1 for ordinary text, 3:1 for qualifying large text and applicable non-text control boundaries/focus indicators. Disabled controls are generally exempt from WCAG contrast success criteria but should remain distinguishable and readable where practical; never communicate state through color alone. Use accessible typography, labels, focus visibility, zoom/reflow and visual/screenshot regressions in light/dark system settings, desktop and mobile. One coordinated color-token pass is insufficient without component/state measurements. No backend or schema change is expected.

The current `review_files.py::validate_round_file` explicitly permits only `.pdf` for confirmed first-round Initial Editing; later author revision files follow `ALLOWED_MANUSCRIPT_EXTENSIONS`. `eic.py::confirm_pre_review_version` also checks `%PDF-`; `migrations/001_reviewer_file_bindings.py` links round one to the author confirmation and later rounds to formal revision, without encoding a file extension. A safe multi-format design must explicitly extend content validation and confirmation/download checks while retaining EIC approval, author confirmation, immutable assignment-specific binding and old PDF behavior. Do not change any historical `review_round_files` or `review_assignment_files` binding merely to enable new formats. `migrations/006_formatter_publication.py` and `formatting.py::verified_file` bind the published formatting submission and its hash: preserve exact approved bytes, integrity and actor/approval checks.

Plan a shared extension/content validation contract without trusting browser MIME: PDF signature and policy; DOCX ZIP/OOXML structure with bounded entries/decompression and macro/active-content policy; legacy DOC OLE signature plus stronger type inspection as justified; TXT explicit supported encoding (for example strict UTF-8 with an agreed BOM/line-ending policy), size and binary/control-character rejection. Signatures/structural checks reduce mismatches but do not prove documents harmless. An optional, vetted OLE parser can distinguish legacy Word from arbitrary OLE; `.doc` parsing or trustworthy browser preview may need a sandboxed, separately reviewed dependency. Support all four upload formats even if preview is unavailable: provide authenticated safe download fallback and never silently convert. Decide whether PDF-only publication proof is mandatory; if so, define an explicit, separately reviewed conversion or additional proof artifact and bind approvals to exact bytes, without overwriting, replacing or deleting originals. If no conversion is approved, show DOC/DOCX/TXT as downloads and allow only approved workflow outcomes compatible with the chosen proof policy.

`manuscripts.py` uses unique generated storage names; general and assignment downloads currently synthesize `manuscript_<id>...` names, while version listing uses stored generated filenames. Thus original user-supplied filenames are **not** consistently preserved today. A future additive, safely sanitized per-version display-name/content-type association may require a separately approved migration; avoid changing old records, and use safe generated names for historical files with no trustworthy original metadata. Send correct MIME, `Content-Disposition` and safe fallback names; defend against path/header injection. Update `EICDashboard.jsx`, `InitialEditingPanel.jsx`, `FinalEditingPanel.jsx`, `FormattingPanel.jsx`, `EditorDashboard.jsx`, `AuthorDashboard.jsx`, `ReviewerDashboard.jsx` and any shared API helper as appropriate.

Keep the present 10 MB ceiling unless separately approved, with clear empty, unsupported, malformed, MIME/extension mismatch and oversized errors.
